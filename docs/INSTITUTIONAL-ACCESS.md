# Institutional access and administrator oversight

## Sign in as the initial administrator

The project owner explicitly selected **tevi87637@gmail.com** as the initial administrator. It has an exact-account domain exception; **gmail.com is not an approved domain**. No institution domains are enabled by default.

1. Open `/login` and sign in with the existing account and password.
2. Choose **Set up authenticator**, scan the QR using an authenticator app, and enter its six-digit code. Never share or screenshot the setup key/QR.
3. After verification, open **Admin Oversight** in the sidebar (`/app/admin`).
4. Independently verify the requesting institution's ownership and approve its **exact email domain**, with the organization name.
5. Users create access requests and verify their email. Approve each account separately and assign VIEWER, INVESTIGATOR, or ADMIN. ADMIN grants project-wide access; do not assign it to every domain member.
6. Assign approved operators to cases. Disabling a domain or suspending an account blocks subsequent workspace requests, including direct database reads. In-flight operations already authorized may finish.

Example: approve `department.example.org` only after checking the organization. That does not approve `sub.department.example.org` or `department.example.org.attacker.net`. `cmrcet.ac.in` was the user's illustrative example, not an authorized production domain, and has not been added.

## What the administrator sees

- Project-wide case, operation, audit-event and account counts.
- Exact domain approvals, disable/reapprove controls, and requested domains derived from pending accounts.
- Account approvals, rejections, suspension and role assignment; no self-demotion or self-approval through this screen.
- Case membership assignments and links into case timelines.
- Global application timeline, 100 newest events per page, including actor, time, case, session and integrity hashes; before/after records for domain/user policy changes.
- Latest 50 operations with saved status, result, duration and throughput where recorded.
- Up to 200 provider auth log records and 200 session metadata records. No passwords, tokens, password hashes, QR secrets or OTP codes are exposed.
- Counts and overview poll every 20 seconds while visible. Refresh reloads the latest timeline; older timeline pages remain stable while reviewing.

Provider authentication logs were empty at implementation time. The UI explicitly says when no provider records exist; the application timeline still contains recorded session events. This is **not a claim that every failed password attempt or all external database/website-code changes are captured**. Supabase retention and auth-log configuration determine available provider records. A stored RUNNING operation or session record does not prove the worker/user is currently online.

## Enforcement

Cloud requires verified email, an active server session, exact domain approval (or the single approved-account exception), APPROVED account status and `aal2` MFA. The Edge API checks the user's validated session, and restrictive RLS policies gate all eight application tables. Storage remains private and is accessed only through authorized API downloads. Admin RPCs are service-only; policy mutation and its before/after audit event commit atomically.

New registrations may create a Supabase Auth identity and a pending profile, but cannot enter the workspace or read case data. Authentication is distinct from authorization. No suffix-based government/college auto-approval and no client-controlled roles are used.

The original Python/SQLite mode is a local development demonstrator. These institutional-domain/MFA controls protect the connected Supabase cloud deployment; do not expose the local development backend as an institutional production service.
